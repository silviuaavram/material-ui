# Testing component contracts

Use the harness and commands in [AGENTS.md](../../../../AGENTS.md). Start with the smallest test that can fail at the component's boundary and grow coverage where a distinct code path warrants it.

| Layer                   | What to check                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Material UI API         | Select relevant [conformance checks](../../../../packages/mui-material/test/describeConformance.ts) for root, ref, theme, and exposed slots. Omit checks for capabilities the component does not support.                                                                                                                                                                        |
| Public types            | Use a nearby `.spec.tsx` for supported combinations and deliberate compile-time rejections. Use a consumer [module augmentation fixture](../../../../test/moduleAugmentation/material/numberFieldCustomProps.spec.tsx) when extending theme or slot types is part of the API. Confirm the fixture uses updated build declarations if it resolves published package entry points. |
| Interaction             | Check interaction and handler behavior introduced by the component or changed by composition. Assert the outcome, target, order, cancellation, or call count that could regress. Check controlled and uncontrolled paths where they differ, and rerender when behavior depends on live props or context.                                                                         |
| Accessibility and forms | Query by role and accessible name. Check description, keyboard tab and focus behavior, disabled and read-only behavior, and custom rendering paths that can break them. For form controls, inspect `FormData`, native validation, or submission when the adapter affects them.                                                                                                   |
| Rendering and styling   | Test initial markup and hydration if a parent derives state synchronously or IDs cross elements. Use computed styles for theme wiring and actual layout measurements for geometry. Exercise demo screenshots and axe via the repo's harness where relevant. Automated accessibility checks complement keyboard and focus tests.                                                  |

## Choose regressions at the integration boundary

[NumberField tests](../../../../packages/mui-material/src/NumberField/NumberField.test.tsx) show useful integration probes. A custom helper ID keeps the input's accessible description, a custom render keeps styles and refs, and a non-native stepper activates once. Prefer these over duplicating the primitive's numeric arithmetic or the underlying Material UI component's generic behavior. Use the default variant and size unless they exercise a different branch. For example, variant style preservation has distinct leaves, while helper ID wiring is shared.

## Match the test environment to the failure

Use a real browser where the assertion depends on layout, native behavior, or pointer APIs. The NumberField drag test needed explicit movement deltas because user-event does not generate them. Firefox could finish releasing pointer lock after the test's pointer-up call resolved, so an immediate assertion could fail on CI. Drive the actual interaction, then wait on the observable state or callback with `waitFor`. Keep assertions about timing that the API promises and avoid fixed sleeps or browser-specific workarounds unless the behavior itself differs.

## Review the docs as consumers see them

Pick demos that explain distinct usage and match the public types. Show meaningful variant and theme differences, including dark mode for color overrides where relevant. Document the keyboard model, slot and ref behavior, and precedence consumers would otherwise have to discover in source. Check generated API output for unions, defaults, exports, and class names as applicable. If renaming a demo, search both screenshot and docs E2E routes and baselines for the old name. See the [NumberField guide](../../../../docs/data/material/components/number-field/number-field.md) and [docs E2E baseline](../../../../test/e2e-website/demo-docs-production.baseline.ts).

When iterating on a single component's generated output, use `pnpm proptypes --pattern ComponentName` and `pnpm docs:api:build --grep ComponentName`. The full `docs:api` script clears the generated directories first, so reserve it for a full rebuild. Inspect the resulting diff for stale metadata and unrelated churn.
