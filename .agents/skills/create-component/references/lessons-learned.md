# Lessons from NumberField

These cases come from the available development discussion, committed changes, and the current NumberField implementation. The actions describe what to do when a future component has the same problem.

## Map primitives to elements before exposing slots

NumberField initially exposed a separate Group slot. The group and Material input root both wrapped the same input and adornments, giving consumers two customization points for the same region. The final implementation keeps the Material input root and applies Base UI Group behavior to that element through a private adapter. The wrapper retains Material styling and click-to-focus, and the native input remains separately customizable. Apply this when two layers can share a host and forwarding contract. Keep separate slots where the elements have distinct ownership or customization needs. See [input root adapter](../../../../packages/mui-material/src/NumberField/NumberFieldInputRootSlot.tsx) and the `input customization` suite in [NumberField tests](../../../../packages/mui-material/src/NumberField/NumberField.test.tsx).

## Resolve behavior once and configuration at the right scope

Disabled, required, and read-only appeared in both Material props and Base UI state. Raw props alone missed states resolved by the primitive and its field context. NumberField passes the requested flags to the primitive and uses its resolved flags for Material rendering. Material still owns presentation such as size and color. Resolve by responsibility rather than applying a blanket spread order.

The root also needed to inspect the input slot's start adornment. Evaluating that callback again at the input made its result depend on which layer read it. NumberField resolves callbacks shared by multiple consumers once with the agreed state, while position-aware adornment callbacks stay local to each rendered instance. Apply this when a slot result feeds multiple outputs, such as a label, the input, or first-render layout. See [NumberField root composition](../../../../packages/mui-material/src/NumberField/NumberField.tsx) and [adornment slot](../../../../packages/mui-material/src/NumberField/NumberFieldAdornmentSlot.tsx).

## Trace overlapping prop paths to the final DOM spread

NumberField inherits a styled input with its own prop bags. The public placeholder originally reached the outer root, and passing merged props down alongside deeper input bags let InputBase's later spread replace composed handlers or refs. The adapter sends field props to their intended element and consumes competing native prop bags before composing with the primitive. Its documented order is wrapper keyboard handlers, then `htmlInput` (replaced by explicitly present `inputProps`, even if undefined), then nested `slotProps.input`. This is a NumberField compatibility decision. Choose a narrower surface for a new component when consumers only need one path.

Check which inputs support callbacks and resolve those before spreading. Check the difference between omission and explicit undefined. NumberField filters nullish event handlers _after_ choosing the winning consumer props, so clearing an earlier consumer handler cannot erase the primitive's internal handler. Refs are merged separately. Keep these rules close to the adapter unless more callers share the same contract. See [resolveInputProps](../../../../packages/mui-material/src/NumberField/utils/resolveInputProps.ts), [nullish handler filtering](../../../../packages/mui-material/src/NumberField/utils/omitNullishEventHandlers.ts), and [InputBase rendering](../../../../packages/mui-material/src/InputBase/InputBase.js).

## Separate changing a host from replacing a slot

NumberField moved from `component` to `render` for changing the underlying element while retaining behavior and styles. A replacement in `slots` takes precedence and owns its styling. Merely removing `component` from the types left a runtime path where JavaScript callers could still cause `useSlot` to bypass the styled component. The component clears the unsupported prop and uses private bridges where necessary. For future APIs, define the distinction intentionally, then check it in types, at runtime, and with actual consumer props forwarded to the host. Existing components may still need their public `component` contract. See [root slot](../../../../packages/mui-material/src/NumberField/NumberFieldRootSlot.tsx), [render bridge](../../../../packages/mui-material/src/NumberField/RenderElement.tsx), and [public type checks](../../../../packages/mui-material/src/NumberField/NumberField.spec.tsx).

## Give keyboard activation one owner

A non-native stepper could get synthetic activation from both the behavior primitive and ButtonBase. An early fix keyed the shared ButtonBase hook off a private Base UI event flag, which coupled unrelated ButtonBase consumers to the primitive. The final implementation keeps the coordination in the stepper adapter, uses the standard default-prevention contract, and shares native activation detection with ButtonBase. The change to ButtonBase's public keyboard behavior has a migration note. Apply this when composing two layers that might synthesize click. Verify Enter, Space, cancellation, and any supported native links or buttons, including the one-activation invariant. See [stepper adapter](../../../../packages/mui-material/src/NumberField/NumberFieldButtonSlot.tsx), [native activation helper](../../../../packages/mui-material/src/utils/hasNativeKeyboardActivation.ts), and [ButtonBase tests](../../../../packages/mui-material/src/ButtonBase/useButtonBase.test.tsx).

The default NumberField has one tab stop on the native textbox. The textbox already handles keyboard stepping, and the named stepper buttons remain available to assistive technology. Decide whether a secondary control needs a tab stop based on whether its full function is available from the primary control. Use the actual rendered role in tests. See [NumberField accessibility](../../../../docs/data/material/components/number-field/number-field.md#accessibility).

## Preserve accessible and form relationships across customization

An overridden helper text ID rendered correctly on the helper while the input still referenced the generated ID. NumberField now resolves the final ID once and supplies it to both outputs. Treat an overrideable relationship as a paired contract. For a native label, it is the input ID and the label's `htmlFor` that must match. The label's own ID only matters when something references it.

The visible formatted input and the hidden submission input also have different responsibilities. NumberField forwards `form` to the visible input as well as the primitive root to keep native validation and Enter submission associated with an external form. The primitive owns the submitted numeric value. Apply this distinction when display and submission use separate elements. Verify the accessible description and submitted data, rather than treating matching generated strings or setting `form` on a wrapper as sufficient. See [NumberField composition](../../../../packages/mui-material/src/NumberField/NumberField.tsx) and the `form submission` and `labels, helper text and focus` suites in [NumberField tests](../../../../packages/mui-material/src/NumberField/NumberField.test.tsx).

## Check what a parent can see during server rendering

Wrapping the input in an adapter hid input and adornment information from FormControl's initial child inspection. Updating filled and adorned state later was too late to set the first label shrink state. NumberField supplies a marker component that returns `null`, using the formatted initial text and the same conditions as the actual start adornment. Use this as a diagnostic example when a parent inspects children synchronously. Prefer preserving the existing initialization contract and only use a marker when that integration needs it. Test empty and zero values separately and check initial HTML before hydration. See [root slot](../../../../packages/mui-material/src/NumberField/NumberFieldRootSlot.tsx), [adornment decision](../../../../packages/mui-material/src/NumberField/utils/getAdornedStart.ts), and the `server rendering` suite in [NumberField tests](../../../../packages/mui-material/src/NumberField/NumberField.test.tsx).

## Wire utility classes, theme hooks, and state attributes deliberately

The label, helper, and native input already had public slots, but their `MuiNumberField` override keys were missing. Adding a class key alone would leave the theme rule unused. Named styled slots resolve label and helper styles. The root resolves the `htmlInput` override through a descendant class selector because the variant's own styled input must remain in place. Use this approach for an existing styled leaf when a scoped selector fits the cascade. Verify a computed style on the actual slot and account for which default wrapper supplies the rule.

The DOM also gets state attributes from the behavior primitive. NumberField re-exports the supported namespaces from the dependency and documents their Material slot mapping, including Group → `input` and Input → `htmlInput`. Re-export only when these are part of the intended public API. Confirm the dependency exposes the names and that adapters deliver the attributes to the documented elements. See [root theme wiring](../../../../packages/mui-material/src/NumberField/NumberFieldRootSlot.tsx), [public entry point](../../../../packages/mui-material/src/NumberField/index.ts), and the [guide](../../../../docs/data/material/components/number-field/number-field.md).
